# 编程 Agent 基础契约

SelfMind 是 agent-first 的工作助手。编程能力必须兼容不同语言、仓库、
Provider、CLI 会话和 IM 通道，不能依赖 Go 或运维关键词特判。

## 项目识别

每个 run 开始时，SelfMind 会从 workspace 构建一个有界、只读的
`ProjectProfile`：

- 检查根项目，或最多八个直接子项目；
- 只读取 manifest 和 lockfile，不在组装上下文时执行项目代码；
- 只根据已发现的证据给出候选验证命令；
- 候选命令不是强制命令，agent 执行前仍需读取对应 manifest 和项目约束。

首版支持 Go、Rust、Swift、Node.js、Python、PHP、JVM、Ruby、CMake
和 .NET。新增生态应扩展 `internal/kernel/project_profile.go`，不能在
gateway 路由或主 agent loop 中增加语言特判。

## 编程循环契约

普通编程任务应遵循：

1. 确认当前 workspace，并遵守适用的 `AGENTS.md`；
2. 修改前先检查最小必要的项目范围；
3. 只有真正多步骤或不确定的任务才使用 plan；
4. 遵循仓库现有约定，控制修改范围；
5. 最终修改后运行最小且相关的验证；
6. 把工具错误当作证据，分析环境并调整，不盲目更换命令重复尝试；
7. 汇报修改内容、验证证据和剩余风险。

运行时生成的工具调用 ID 会避开恢复消息账本和本轮所有调用中已占用的 ID，
包括后来被上下文裁剪移除的调用。续接时循环计数重新开始，不能让新动作复用
先前的身份。Provider 原生 ID 与精确待审批调用保持不变；派发账本仍会拒绝
同一 ID 下参数不同的调用。委派调用和兼容调用使用同一套身份保留机制。

运行时会在提示词之外执行同一套恢复纪律。工具尝试会关联当前持久 plan step、
目标、策略和环境。诊断证据产生后允许一次输入有变化的修正；完全相同的重试、
同变更策略的第三个变体，或未知 effect 后再次变更状态，都会在分发前被拒绝。
已证明只读且输入不同的诊断查询仍然可用，继续受原有工具权限和资源预算约束。
此时 Agent 必须先观察当前状态、选择真正不同的策略，或以可执行的阻塞说明结束。
只有当用户、仓库约束或变更本身确实要求可执行验证时，plan step 才设置
`verification_required`；可选验证仍可汇报，但不会让纯检查任务无法完成。
Main 决定真正多步工作是否需要 Plan；工具次数和读写类别不会把可选提示升级为必需。
显式策略和用户要求的规划继续有效。
计划在实质进展或范围变化时更新，无需围绕每次工具调用切换状态。稳定 step ID 自动保留
work-unit 归属，模型无需重复填写。快照省略 ID 时，措辞不变的步骤按原文保留 ID；快照
步骤数不变时，改了措辞的步骤沿用同位置上未完成步骤的 ID，改写措辞不会悄悄替换掉未完成
的步骤。输入有两种明确模式：兼容默认 `snapshot` 列出完整步骤，用于创建、新增和重排；
Plan 已存在时优先 `mode: patch`，只提交变化的 `step_id`/`status`。省略保持当前步骤、顺序和义务，
不删除或取消工作。差量条目必须使用当前精确 ID 并明确状态，不按位置或近似文字猜 ID。
验收条件、必需验证、work-unit 与来源归属仍由同一完整快照校验器处理。
运行时把执行游标与持久版本比较，在同一提交事务中展开差量；模型不填写版本。
版本缺失或过期时，修改前拒绝差量；先观察当前 Plan 并用完整快照协调，再继续差量。
启动时的当前 Run 选择与已提交的直接选择初始化游标；后续已接受回执同时推进游标与完成视图。
回执和 UI 事件仍携带完整已接受 Plan，紧凑输入不改变下文的派发策略。Run 的首个计划还没有 ID（运行时会
忽略收到的 ID），所以每个步骤都要写文字，也不要只为取消而列出步骤；没有文字的条目会被稳定的契约
错误 `plan_step_text_required` 拒绝，错误会说明该 Run 当时有没有计划以及应重发什么。过期 `step_id`
被拒绝时，回执会指出出错的条目，并把每个当前 ID
对应到状态和一个有长度上限的标题。与已声明名称字面相近的未知参数名会被拒绝，并附一句“是否指……”
的询问，绝不替模型改名，因为相近的名称含义可能不同。计划仍有未完成步骤、却已有 12 次工具动作
没有更新时，下一次模型调用的末尾会附一行
提醒，之后要再过 12 次才会再提醒；计划是否仍然准确由模型判断。进度快照放在同批工具调用
首位时，运行时先消费持久保存的实际 Plan，再顺序执行后续调用；每次仍重新检查工具暴露和
中间件。当前 Work Unit、目标、完整有序步骤的身份/文字及验收条件必须保持不变；
已有状态可从 pending 前进至进行中/完成，或从进行中前进至完成。重新打开与取消仍是屏障。
比较覆盖未活动步骤，并规范连续 Work Unit 的归属，不要求当前步骤重复组 ID。
更新失败、状态不可读、第二次 Plan 更新或存在已缓冲的用户补充时，后续动作收到配对的
`plan_boundary_held` 未派发结果；输入保留给 Main，不在此消费。初始 Plan 和语义范围变化
仍单独调用；历史任务选择和独立输入控制保持独占。
同批每一次已接受的 Plan 更新都重新核对原派发边界，包括第二次更新。由循环边界暂缓的
调用撤销其动作预算和生命周期尝试预留，不增加 Plan 活动计数；配对的拒绝证据仍保留。
已尝试执行的失败和未知副作用继续计数，恢复限制不变。报告从已持久化的工具结果重建每个
模型步骤的实际调用与暂缓调用（实时步骤事件不落库）；缺少派发元数据的步骤单独计数，
不从模型请求列表推断执行进展。同样的事实还用于核算失败步骤：含失败工具调用的步骤，按其发起的
那次模型调用的时长计费，并按记录的错误类别分为契约拒绝（输入格式错误、前置条件过期、策略或协议
拒绝）、命令自身结果和其他类别；紧邻的同工具重试单独计数，所有成本都对照该 Run 自己的模型时间
显示。等待人工、策略重定向、被暂缓的调用，以及发起模型调用早于统计窗口的步骤都不算失败。报告还
度量 `update_plan` 参数字符中重复 Run 已存文本的比例，对照其最新被接受的 `plan.updated` 快照；
首个快照、子 Agent 的调用和派发前被拒绝的调用不计入。
新步骤 ID 是 Run 内的短、不透明引用，不代表位置。该 Run 历史上用过的 ID 始终保留；
重排和续接保持原 ID，旧的 UUID 形式也继续有效，无需存储迁移。参数准备会在派发前按稳定路径顺序
一次报告最多八项独立契约错误；保留既有标量/null 兼容行为，不猜状态、不丢弃未知字段、不自动重试。
最终回答不是计划步骤。向模型发布的 `finish_run` 契约要求 `status` 和一份完整
`final_response`；可选 `plan_patch` 和 `assessments` 分别表达最后变化和 Main 的条件判断。
省略 patch 保留当前进度，无需虚构 Plan 或提交无变化更新。简化输入沿用候选状态校验和
原子 finalizer，纯检查任务只提交正文也走该路径；不能与尚未观察结果的工作调用同批。
运行时派生有界展示摘要、实际文件和验证事实，不从正文推断完成、风险或用户接手。
旧的仅摘要与重复记账字段保持原 coordinator 路径，显式提交原子 patch 时除外；旧的
最终 `update_plan` 加 `finish_run` 同批和原生 `final_answer` 处理仍兼容。只有被接受的
完整输出提供最终正文，保留分段并省去再次生成，完成条件不放松。
无需在重复字段重写同一份回答；缺正文、调用被拒或输出不完整时保留收尾请求。
所有协议使用相同注册契约，不按模型名称分支。
Run 状态、回复正文、交接和终态事件沿用既有原子收尾事务。提交失败时给出可恢复的阻塞结果，
不能对外报告完成；原工具证据继续保留，已完成的副作用不得重复执行。
和 `finish_run` 写在一起的回答，后面再跟一句收尾也不会丢。
被计划核对打回的那次最终回答不保留。因输出上限而续写的回答拼回产生它的那条
assistant 消息；被拒调用配对的工具结果保留各自内容。续写的回答只属于一次作答：被计划
核对打回的回答不会拼到下一次回答前面，执行动作类工具会结束这次作答。被拒绝或因预算被
丢弃的调用同样结束这次作答：带有自身正文的回复补完待续写的截断回答，之后若不再给出修复
提示，就以拼接后的完整文本作答，与没有截断时一致；没有正文的回复补不完任何内容，待续写的
截断文本直接丢弃，不作为残片带入后续回答。被截断或被过滤的回复中含不完整的调用时，待续写的截断
文本连同该回复一并丢弃，因为两者都不是完整回答。只伴随 `update_plan` 或 `finish_run` 的续写正文按顺序保留在
最终回答中，不带正文的计划或结果调用则让被截断的回答继续等待续写。重新从头作答时替换被
截断的部分，即使空白或空行的排布不同也一样，被服务商过滤的回复同样如此。计划核对依据运行时接受的快照，
而不是模型请求的快照：运行时保持待办的取消仍是未完成步骤，计划修复会点名它，本轮
不能以完成结束。工具结果读不出计划时，沿用上一次接受的快照；尚未读到任何接受的快照时，
计划核对按模型请求的快照从严判断，请求取消的步骤也算未完成。

进度快照省略已有步骤的验收条件或必需验证标记时，系统保留原值；取消必须明确表达。
已完成步骤改写验收条件时，工具向 Main 返回有界的原条件与现条件对照，由 Main 判断
用户的范围变更是否支持这项修改。Main 同样区分用户明确接手剩余工作与没有交接依据的
必要未完成工作：前者可以按约定范围结束 Agent 的责任，后者保持未完成。仅建议用户
执行下一步不能构成交接。缺少最终回复不会覆盖已经确定的执行阻塞原因。

新 Run 使用 v3 恢复契约记录取消判断。Main 给出 `cancellation_disposition`
和 `cancellation_reason`：确已无必要或已被替代时使用 `not_required`；用户明确接手时
使用 `user_takeover`；必要工作仍未完成时使用 `unfinished`。`not_required` 需引用
已完成且保留该步骤既定验收条件（首个非空条件）和必需验证的 `replacement_step_id`，
或说明范围变更的真实用户原话 `scope_change_quote`。规划时没有验收条件的步骤无条件可
保留：取消所引用、已完成且写明自身验收条件的替代步骤即可覆盖它。单纯失败不构成这两类
证据。运行时核对引用的 Plan 状态和原话来源，Main 判断是否覆盖目标。用户接手还需提供
`user_takeover_quote`。两类原话都必须逐字复制自同一人精确续接链中某一条真实用户输入
或已消费的补充指令，排除其他任务与 daemon 生成的文字：可以是整条消息、其中完整的
一句，或按词边界对齐、至少两个词和八个字母（每个 CJK 字符按两个计）的部分片段。因此
“no need”“我来”这类完整的简短指令可以作为原话，“the”这类片段不行。标点不构成语义否决：
Main 判断指令（包括礼貌问句）是否改变范围或明确交接，找到原话只证明来源。编号和缩写不算
句子边界，代码块不提供整句。可能被截断的
文本（以“...”结尾的 Run 摘要，或证据被截短的开始事件文本）不提供整条消息或最后一句，
部分片段也不能止于截断处。运行时会记录通过校验的原话匹配到的输入（续接链上最早的一条）并随计划
展示；模型无法自行填写。原话是否构成交接，以及后续
修正是否改变范围，仍由 Main 判断。缺少判断或必要工作未完成的取消保持待办，计划更新会
指出唯一缺少的事实（没有处置、没有证据、替代步骤未完成或不存在、验收条件被改写或未写明、
丢弃了必需验证）以及可执行的补正方式。完整快照遗漏未完成步骤时，保留其精确 ID 和验收条件。这些信息随既有 Plan 跨重启与续接
保留；升级不重写历史 Run 契约或快照，也不为历史数据增加权限。

命令证据分别保存工具调用与进程观测。进入工具处理不代表进程已启动。结果分别统计
尝试次数、已观测启动、已观测非零退出、未派发、派发未知与退出状态未知。历史缺失
信息保持未知，除非同一 Run、同一调用有类型化的持久完成观测。这些统计不构成绑定
验收条件的验证结论。

`verify` 原生暴露 `step_id`、`criterion`、`target`、`local_dependencies`、`replaces`
和 `reason`，兼容旧的嵌套 `check` 形状。声明了条件或目标但没有 `step_id` 的检查保持独立，
即使文字相同也不能完成 Plan 步骤。Main 明确选择运行时发出的步骤 ID，包括待办步骤，
常规调用只需 `command` 和 `step_id`，条件和目标继承已保存的验收项，无需先更新为进行中。
未指定条件和目标的检查保留既有当前验收项默认值。Plan 描述结果里程碑，
不为读 Skill、审批或重试新增步骤；更新仍为完整快照。

修正方法时，Main 用 `replaces` 引用原检查并说明 `reason`，保留条件、目标与工作目录。
条件和目标无需重复填写。原步骤关联保持不变；绑定另一当前步骤需明确提供 `step_id`。依赖声明和既有替换投影负责
有效性判断。原尝试保留在历史中，结构校验不能证明语义充分，未绑定的历史检查不获得替换权限。

验证使用 Bash 的 `-e` 和 `pipefail`；预期会出现的非零退出需要显式条件分支处理。
观测到非零退出会记录失败证据，并不自动要求重试：条件不成立还是检查方法出错，由 Main
判断。报告负面结果不等于验收通过；Main 不应为收尾反转检查，或把条件改成“结果已查明”。
工具回执报告错误、捕获输出和证据引用，不指定 Plan 状态转换或重试步骤。内部恢复
字段仍作为类型化事实持久保存；用户决定和未知副作用在模型回执中仍明确可见。

执行事实、条件判断与目标完成分开表示。既有验证 `state` 保留命令与检查事实，
不代表 Main 对条件的结论。Main 可随 `finish_run` 可选提交 `assessments`，每项提供
`result`（`met`、`not_met`、`unknown`）和简短 `reason`。Plan 条件优先用 `step_id` 选择，
由运行时绑定有效证据；需要精确选择时，可改用当前 Run 的 `evidence_refs`。
两种选择器不可混用。步骤必须只有一个条件、目标、工作目录和来源；多目标时不能猜选。
历史检查只能来自已接受步骤的明确采用，步骤选择本身不授予采用权限。
运行时解析并重新校验证据，保留 Main 的判断；当前检查保存为 v1，采用历史检查的判断保存为
v2，附原始检查 ID 与独立的来源 Run、步骤和 Plan 版本，不伪装成当前执行。
沿用既有 outcome JSON，无 SQL schema 迁移；v1 历史记录不因此获得采用权限。
历史缺失判断保持未评估。调查与报告里程碑若不要求正向验收，可以带着有依据的负面发现完成；
必需的正向里程碑仍需通过验证，条件为不满足或未知时不能完成。Main 根据用户目标设定义务，
运行时不移除已有要求。无关的成功检查、后续未附判断的 outcome 都不能抹掉未解决结论；
输入变化会使旧判断失效。续接将旧判断作为历史上下文展示，不把负面发现采用为正向证明。
不是当前 Run 有效检查的引用会作为可纠正输入被拒绝，且不会选中其他 Run 的观测（调用 id
在每个 Run 中重新计数）。拒绝信息列出当前可引用的检查；若该 id 是某个已导入步骤背后的
观测，还会指明该步骤以及运行时是否会采用它，这样读到旧记录中 id 的模型能直接知道出路，
无需自行重建证据边界。`verify` 的 `replaces` 遵循同一规则。
执行证据或结构化结果保存失败时工作保持未完成；恢复存储不能重复已完成的副作用。

精确续接在继承 Plan 的同一事务中，将直接来源检查引用写入既有 Work Journal。多次机械等待
不再因旧版有界链窗口而丢失原观测。这仍是历史上下文，不自动完成工作：Main 用
`reuse_prior_verification` 和理由明确采用仍有效的检查。运行时检查精确来源、本人执行范围、
未变的里程碑与条件、有效检查结果及中间依赖变更。检查成功已保存、Plan 记账前中断，也可以
续接后明确采用；另一个目标未解决的失败仍阻止完成。未知变更保守失效，历史快照不重写。
提示切片保持有界，并明确说明省略了多少证据引用。

已接受的独立来源检查不会因无关写入而被要求在当前 Run 重跑；当前失败的检查仍阻止复用。
最终 Plan 的准备阶段重新打开步骤时，沿用既有验证延迟投影并附上原因；拒绝信息明确说明
候选未提交，已保存的 Plan 保持不变。完成前提失败且确定未派发后，后续成功检查或已接受的
变化 Plan 可以恢复收尾额度，每个循环最多三次。无变化更新、失败检查、拒绝和未知效果
不会恢复额度。纯输入纠错继续由独立的 Run 预算和重复保护约束。

精确续接是运行时恢复同一项工作（审批或澄清的回答、watcher 结果、恢复、资源或 Provider
唤醒），因此从 parent 记录的 Plan 起步。已完成且要求验证的步骤保持完成，并在同样的来源、
范围与新鲜度校验仍通过时，以运行时写入的理由从来源采用，跨任意多跳直至血缘上限。只有来源
不再通过校验的步骤（检查失败或只部分结论、输入或条件变化、执行范围改变、血缘超出上限）才会
单独重新打开；parent 的进行中步骤保持进行中，否则最早重新打开的步骤成为进行中。用户的一次
输入以及由 Main 选择的续接保持保守导入：已验证步骤重新打开，直到 Main 采用或重检。携带不授予
任何东西；完成时仍会重新校验每个被采用的步骤。被携带的步骤只是“没人再看过”的默认值：本 Run
为它做了检查后，以该检查为准，已保存的 Plan 不再声称旧观测，失败的复检也不会被它掩盖；
Main 自己明确采用的步骤保持原规则，与当前检查冲突。

选中的上下文将有界的未解决外部效果阻塞与 Plan 里程碑分开。`verify` 可用同一次只读观测
绑定 Plan 步骤和 `effect_claim_id`，本链与外链的既有释放规则保持不变。最终结果显示与本轮
有关、运行时仍未解决的占用，不因模型文字声称释放而消失；这不结算占用，也不授予执行权限。

新 Run 会启用版本化恢复契约。若 daemon 或 Provider 中断且尚未产生外部 effect，
系统可以幂等地排入一个精确指向 parent Run 的 child Run；若已分发 effect 但结果不确定，
则进入 verification-only 恢复：只暴露可信的只读工具，并在分发边界拒绝 mutation。
审批、澄清和 external watch 仍由各自专用恢复路径负责；历史 Run 不会因为二进制升级而
自动获得执行能力。尚未开始的自动恢复优先级低于用户新提交的前台工作。

长时间外部等待保留模型定义的原目标、验收标准、未完成计划、用户纠正和精确目标证据。
模型负责业务标准与只读观察方法；运行时负责有界执行、持久调度、审批和恢复。
观察条件满足只代表恢复工作，不代表整个任务完成。

新观察回执（版本 2）的正则检查必须选择一个有界标量，并匹配整个值；文档、日志和
嵌套成功标记不能作为标量输入。现有类型化 adapter 仍可使用。模型通过现有命令或
已授权观察脚本选择字段、映射状态，gateway 不增加供应商分支。预检记录命令哈希、
环境 generation、目标、截止时间和实际生效能力。注册时已达到终态的观察也持久化
为 `all`/`any` 等待组成员；成员齐全才交接。创建 Run 已结束或截止时间已过而成员
仍不齐的组报告检查失败，不能报告外部操作失败。聚合结论和续接保持幂等。

版本 2 的续接在原执行范围内恢复 Main 的正常工具与审批路径。Main 根据剩余标准
核对证据、补充检查、完成已授权工作，并通过 `verify` 完成必要验证。不能悄悄降低
标准或重复已完成的副作用。历史回执保留原匹配与 file-only 收尾策略，升级不会为其
新增权限。terminal 在审批和执行之前检查 shell 语法，防止复合命令前半段已经执行
后才发现后半段语法错误。

审批证据区分用户原话与 daemon 生成的恢复提示。新 Run 在启动事件中保存带版本的
审批意图快照。版本 2 同时冻结用户回复前看到的方案，并在精确父 Run、相同工作区与
执行根目录的恢复链内传递最多六份带来源的用户原话，后续追加要求保持独立。
审批模型按用户接受的范围与操作影响判断，不依赖同意词表；理由应指出用户证据或
缺少的执行权限。系统文字不能生成用户禁令，也不能授权操作。证据不完整时明确标记；
历史意图证据缺失或版本不支持时，
相关执行需要人工确认，避免把通用质量要求误当成对所有操作的禁止。

完成状态必须由证据决定：

- `completed`：工作完成且相关验证通过；若没有可执行验证，需要明确说明；
- `verification_partial`：实现已完成，但部分验证无法执行或没有结束；
- `waiting_user`：需要审批、凭据、外部依赖或用户决策；
- `blocked`：确认存在外部阻塞，无法继续取得有效进展。

仅写入文件或工具返回了输出，都不能单独作为完成依据。文件变更、命令结果、
artifact 和 run event 才是证据面。完成检查独立分页读取 Run 证据，不受进度消息数量
影响。回答中提到的文件名仍是文字陈述；只有观察到的文件变更才进入 changed-files
元数据与自动文件产物。

## 平台边界

Linux 是执行能力最完整的平台，terminal 可以使用配置的隔离沙箱，并在需要时
通过审批升级权限。

macOS 支持 CLI、daemon、Provider、workspace 工具和 LaunchAgent 生命周期，
但不具备 Linux 隔离沙箱：

- `sandbox.mode: auto` 降级为受审批控制的宿主机执行；
- `sandbox.mode: isolated` 或 `sandbox.required: true` 会 fail closed；
- `/diag` 和 `selfmind doctor` 必须明确展示这个边界。

原生 Windows 不是正式执行目标，Windows 用户应使用 WSL。路径和 shell 行为
必须由运行平台决定，不能根据用户提示词猜测。

## Operator 提示词工作区

深度用户无需增加配置键，就能调整静态提示词层。当前配置文件同级目录是唯一
来源（通常为 `~/.selfmind/prompts/`）：

- `agent.md` 管理前台人格和表现偏好。仓库中的 `AGENTS.md`/`.selfmind.md`
  仍是较低信任级别的项目上下文，不能替代 operator 层。替换或关闭 Progress
  Updates 会改变 transcript 形状，因为每条工具调用前的 preamble 都会持久化为
  独立 assistant 消息。每个主前台 turn（包括不暴露工具的纯直答）都会保留锁定的
  响应与交互底线，用来约束语言跟随、结论优先、有限澄清、面向终端的标题、平铺列表、
  代码与路径格式、不使用固定报告模板，以及默认不倾倒原始协议，但不对使用者职业作
  任何断言。锁定的工作质量底线同样不依赖具体能力，即使没有
  模型可见工具也会用于前台和委派工作；只有绑定 workspace 时才加入工作区实现指引，
  而且只有存在命令能力时才要求命令验证。生命周期指令由当前 turn 实际下发的工具
  定义生成，因此只读 finalizer 或受限角色不会被要求调用它没有的计划、终端、Skill
  或结束工具；
- 委派 Agent 只从同一冻结快照继承适用的工作风格、验证和语义条件式用户界面指引。
  系统不通过关键词分类器判断是否适用；提示词自身声明适用边界，并要求模型在其他
  任务中忽略它。委派 Agent 保留面向父 Agent 的专用身份，不继承 Persona、
  Progress Updates 或 Persistent Learning。
  委派上下文会保留父任务的取消、workspace/run 权限和 artifact，但使用全新的策略
  与延迟工具激活状态，也不保留对话记忆。子 Agent 默认使用父 run 的模型（`delegation`
  另行指定时除外），以父 run 的 person 身份执行工具，只把工具活动、证据和用量标记为
  delegated 转发到父事件流；它的流式文本和轮次生命周期不进入父事件流。父任务拥有的
  计划、结束、watch、memory 与 Skill
  变更工具不会下放；结果以 evidence/files/tests/blockers 的结构化交接返回；
- `background/memory_extract.md`、`background/background_review.md`、
  `background/skill_curator.md`、`background/summarizer.md` 与
  `background/semantic_recall.md` 只影响对应角色/任务。后台复盘不会继承前台
  `agent.md`、通用任务策略或仓库指令文件。模型只看到 memory 与 session 证据工具；
  仅供验证器使用的 Skill 读取工具仍留在内部。对话快照按不可信数据围栏；
- 新生成模板以独立成行且格式精确的 `selfmind:section`/`selfmind:end` 标记作为兼容
  边界，因此标记章节内的 Markdown 标题只是普通自定义内容，Markdown 代码围栏
  内的标记示例也仍是正文。首版生成的无标记文件继续兼容，但其中固定二级标题仍
  保留为章节边界；使用 `selfmind prompt edit` 打开时会迁移到新语法，并在旁边保留
  带时间戳的原文件备份。`default` 继承代码内置指引；只有明确可替换的
  表现层章节接受 `off`。自定义质量指引追加在锁定的 schema、治理、工具和安全
  契约之后，不能删除这些底线。

daemon 在启动时加载并校验一份不可变快照，turn 执行期间不读取提示词文件。有效的
活跃快照会成为该 prompt root 明确的最近一次有效 revision。活跃工作区无效时，
daemon 会继续开放 CLI、IM、cron 和 HTTP 端点：优先使用同一 root 的最近有效快照，
若不存在匹配的激活记录则使用内置默认。它会写入持久、脱敏的降级状态事件和日志
告警，`selfmind doctor` 会报告无效文件与实际选择的来源。校验本身不会放宽：prompt
root、嵌套目录或文件上的不安全权限与符号链接，以及错误标记和未知章节仍会被拒绝。
`prompt validate` 与 `prompt apply`
仍然严格；活跃工作区无效时，显式执行 `gateway restart` 也不会先停掉健康运行中的
daemon。

快照 identity 只覆盖解析后的章节值，不受注释或文件排版影响。持久维护 payload
会固定该哈希和本地内容寻址 revision，因此重启后的重试不会改变模型契约。daemon
会用已验证的当前快照修复其损坏缓存，并尽力持久化内置回退 revision，但不会把它
提升为最近一次有效快照。历史 revision 缺失时，相关工作进入
`blocked_prompt_revision`，不会误报 provider 故障或静默换用新版本。恢复历史
revision 后，`selfmind maintenance replay` 会显式把相关最新 generation 作业送回
队列。revision 只包含静态资产，不包含任务数据、memory、项目上下文或凭据。

上下文压缩使用锁定的 summarizer system 契约，并把待压缩状态放在独立的数据围栏
消息中。交接必须保留活跃目标和 plan/work unit、验证状态、不能重复的失败尝试、
审批或外部等待状态、精确标识符，以及相关文件路径。一个有界的结构化路径后备会
补齐模型遗漏，并在超过安全上限时显式报告。operator 的摘要指引可以调整侧重点和
语言，但不能替换这些恢复执行所必需的章节。

Eval 无视 operator 工作区，强制使用嵌入默认值和空 identity。提示词加载、长度
限制、插入位置、revision 固定和默认字节稳定性由机制型 Go 测试证明，不依赖
provider replay cassette。

## 回归门禁

编程循环的行为变更必须同时具备：

- 所属 package 的聚焦 Go 测试；
- 用户可见 message-path 变化对应的 coding eval；
- Linux 上运行 `go test ./...`；
- CI 中的 macOS build/test；
- 所有发布平台 npm package 的 smoke test。

录制后的 eval cassette 才是确定性的发布证据，单次 live provider 成功不能替代
发布门禁。
