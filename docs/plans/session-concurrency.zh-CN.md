# 同一人多 Run 稳定并行方案

> 生命周期：active（2026-09-29 起；以 `docs/manifest.yaml` 为准）
> 批准：项目所有者（2026-09-29）；复审：2026-10-10
> 基线：`docs/execution-concurrency-plan.md` 的安全不变量、现有 Run + Work Journal、`docs/identity-continuity.md` 的 Phase-1 北极星。
> 当前能力：仍然每人最多一个正在执行的顶层 Run。以下是目标，不描述已实现的功能。

实施记录（2026-09-29）：批次 A 的事件受众投影、CLI 跨窗口普通输入排队、精确 Run 回复边已在独立工作树实现，快速自检通过。实时与回放共用同一投影；跨窗口的明确回复边可经消息路径补充目标 Run，缺少来源执行范围的薄客户端直接 steer 仅限原会话。多窗口同时运行的生产路径 eval 尚未建立，批次 A 未通过完整验收。原子多 Run 准入、IM 单聊多工单路由与资源隔离也尚未实现，因此执行上限仍为一，不能将当前状态称为“并行已可用”。

批次 B 的存储边界已开始收紧：被领取的队列项与新 Run 在同一事务内绑定，旧领取者不能回退或结算新领取者的队列项；daemon 关闭及 watcher 对已绑定但效果不确定的 Run 保留精确归属，不从队列顶端重放。旧版本可能留下的“queued 但已绑定 Run”项也不会被再领取，启动恢复保留原 Run 身份。队列绑定成为中断 Run 的持久工作证据，避免未执行到 Plan/工具阶段的已接受输入从 Attention 消失。watcher 收尾 Run 已完成而结果投递回执未落库时，现从原 Run 的持久回复补投，不重跑工具。这些是原子多 Run 准入的前置故障边界，尚未改变执行容量或路由语义。

后续实施记录（同日）：控制层新增事务内每人 Run 容量检查，并以两个独立 SQLite 连接的并发竞态证明单名额只有一个赢家；Gateway 已把当前容量 1 交给该检查。活动注册表改成每人多个精确 Run 句柄，更新、异常恢复和退出按各自句柄操作；显式 steer、停止、状态详情和 watcher 保护按 Run/Task 定位，含糊的裸停止拒绝猜测。两个 CLI session 在测试容量 2 与双 worker 下真实重叠进入模型，旧默认仍为 1。详细事件受众、digest 计划与最近活动只取对应 Run；同一目录的符号链接别名也被物理路径冲突锁识别。多个活动 Run 的无目标 IM 输入暂以持久选项保存，请用户精确选择；目标在回答前结束则把原文保存为后续队列工作。这是防止误送的保守兜底，尚未达到 Main 自主语义路由。新增模型无关的 `/status <run_id>` 评测。尚缺 IM 单聊 Main 路由、外部目标占用、受管 Git 视图、provider 限流、2/3 容量的实机故障矩阵和发布验证；这些完成前不得开放并发默认值。

补充实施记录（同日）：多活动 Run 的选项答案现将选择和原始输入的 mailbox/队列去向在同一控制库事务提交；写入失败保留待答选择，目标恰好结束则绑定原 Task 排队，双连接抢答只有一个赢家，答复回执丢失后的相同选择可读取原去向而不重复提交。队列名额竞争不再复制输入，一次 drain 可依次填满多个空余名额；目录冲突的队首不会占据空闲名额，同来源的后续项保持顺序，其他来源的独立项可以启动。目录判断与 worker 共用物理路径归一化；同一 CLI session 即使有空余 person 名额也不能开启第二个前台 Run，单一 IM 聊天则保留承载多个 Run 的可能。故障注入、跨连接竞态和两个 worker 重叠的 race 测试通过，快速自检 81/81 通过。这些仅收紧 B/C/D 的安全边界，不代表 Main 语义路由、外部资源隔离或默认并行已完成。

本轮续接审查又封住一处丢输入竞态：用户明确选中的 Run 若被恢复链先认领，已确认的队列补充会沿同人、同 Task 的唯一子 Run 关系等待并续接；子 Run 已完成则保持 Task 归属作为新一轮输入。系统生成的 watcher 收尾与自动恢复仍绑定原效果边界，不能被这样改派。来源保序键同时包含平台、账号和 channel，避免同名 channel 互相阻塞。watcher 已全部结束时允许其收尾认领 `waiting_external`，相应离线评测和快速自检 81/81 已通过。

资源复核还发现 `ToolModeLocalRead/Web` 只是提示，未关闭写工具。worker 现仅对真正受运行时约束的无动作/只验证 Run 放开同目录读并行；未知执行根退回 person 串行锁。此改动后的完整发布自检仍待重新运行。远端目标的持久占用、同仓库受管视图、Main 的多在办路由和 provider 限流仍是开放生产并发的硬门槛。

原生 IM 回复边已增加通用的持久发送消息映射：支持返回消息 ID 的平台把回执与出站状态一起落库；入站按 tenant、person、平台、聊天和消息 ID 精确查找 Run、审批或澄清，找不到时不退化到最近任务。Telegram 的 `sendMessage` 与 `reply_to_message` 已接入；其他没有可验证消息 ID 的通道沿用显式短 ID。迁移为 v19，历史消息不会伪造回复边；回执写入被拒时尽力把已接受的发送标为不可盲重试的未确认状态，数据库整体不可写仍需依赖现有崩溃恢复处理。此批未实现 Main 的多在办语义路由，也未开放并发默认值。

接续实施：无精确回复边且同时有多个活动 Run 的 IM 消息先持久化原始选择，再由带独立容量的短 Main 协调 Run 使用主模型和有界 Run 状态卡判断。协调 Run 没有工具和执行根，模型只能选运行时发出的选项；补充与新工作仍由原有原子提交边界落到精确 mailbox 或队列。明确含糊、模型输出无效、超时或并发协调名额已满时保留人的选择。控制库 v20 把历史 Run 标为 work；崩溃的协调 Run 不产生可恢复的工作假象。此处尚缺只读观察、历史续接、跨模型实测与生产多任务验收，故执行上限仍为一。

子代理批处理现按克隆后的实际工具目录判断：所有子代理均只有已知内置读取工具时才使用配置的并行度，并移除嵌套委派入口；任一子代理具备写入、终端、未知或外部工具时，整个批次在父 Run 的共享视图中串行。此举关闭同视图并行写的直接竞态；独立受管视图尚未实现，不能以此作为开放顶层并发的依据。

## 1. 交付定义

同一个人可以同时推进三个独立的真实工作：多个 CLI 窗口各自处理工单；一个 IM 聊天可以查看、补充、审批和发起多个工单。不同物理视图、不同外部目标的工作实际重叠执行；有冲突的工作明确排队。等待人或外部结果的工作保留精确归属和续接能力，同时释放模型 worker。

并发容量不是单独的成功标准。Phase-1 的跨端任务闭环、跨端状态感知、陌生人隔离及 `selfmind eval scorecard` 的任务质量必须保持。CLI 发起 A 时，IM 发起 B，用户从 IM 查看 A/B、补充 A 并回答 A 的审批；A/B/C 各自保留 Plan、工具证据、结果和恢复历史。这组情形是首要端到端验收。

发布门槛：跨人越权、跨 Run 错误路由、详细事件串流、丢失已确认输入、盲目重复副作用和不安全资源重叠均为零；可独立运行的任务在相同工作负载下观察到实际执行时段重叠和总体完成时间改善。每个 Run 的 token、模型调用、排队、资源等待与 429 等待均可归因。

## 2. 归属模型

| 概念 | 唯一职责 |
| --- | --- |
| Person | 同一人的身份、跨端结构化工作历史及并发额度 |
| Channel | 来源、回复与通知目的地；一个 IM 聊天可承载多个 Run |
| Client focus | CLI 窗口当前操作或观看的 Run；仅是展示和默认输入目标，不是权限 |
| Run | 一次执行尝试的状态、Plan、效果、审批、取消和精确控制权 |
| Work history | 从 Run 续接关系、Thread 与 Attention 投影工作历史；不增加新的 Task/Lane 生命周期 |

一个工单可能由出方案、派发、watcher 续接和恢复等多个 Run 构成。列表以工单标题和短 Run ID 呈现；执行和控制始终绑定精确 Run。Thread 标签、最近活动时间、工作区或 CLI 焦点不能授权续接、转交、审批或执行。CLI 默认每个窗口有独立 channel 和焦点；显式恢复同一 session 或 `/attach` 才共同观看。一个 IM chat 的 channel 不占用单独的“一个 Run”名额，所有入口共享 person 的执行额度。

## 3. 输入与补充

1. 身份认证、明确的 Run ID、平台证明的回复边、审批 ID、澄清 ID、`/resume`、`/new --run` 等结构化控制优先，由 Gateway 校验 person、Run 状态、执行范围和一次性消费；无效或过期边不退化为普通路由。
2. CLI 普通输入到本窗口聚焦的活动 Run，先持久保存再回执；Main 在安全节点决定采纳、澄清或作为独立工作排队。其他 CLI 窗口不受影响。
3. IM 一个聊天可同时拥有多个 Run。没有精确目标的自然语言进入一个有界、可审计的 Main 交互，使用现有 `control.db -> selector -> TaskRuntimeContext -> RuntimeContextBundle -> prompt` 路径读取少量结构化在办卡片。Main 可选择观察、补充一个活动 Run、续接历史 Run、开始新工作或询问；运行时重新核对目标与范围。不能引入 run 外分类模型，也不能在目标确定前执行有副作用的工具。
4. 补充到活动 Run 时，持久 mailbox 记录与目标 Run 绑定。目标恰好结束、等待审批或等待 watcher 时，已接受文本不得丢弃、转给另一 Run 或虚报已采纳；回执区分“已保存”“目标已收到”“未在当前执行中送达”，后者走精确父 Run 后续处理。
5. `/status` 总览与 `/status <run_id>` 详情始终无模型可用；IM 消息显示标题、短 ID、阶段和可用动作。序号只解析本 endpoint 最近一次列表的快照；跨端与重启使用稳定 ID。多个审批或澄清同时存在时，未绑定的“同意”“继续”不能猜最近一项。

平台适配器只验证、解析与发送。原生回复要有可持久验证的发出消息 ID → Run/审批/澄清对象映射；不支持的平台使用短 ID 和命令。IM 同时运行的工作只发送带工作标识的审批、澄清、重要里程碑和最终结果，不流式刷工具过程。CLI-origin 结果及 desk-first/phone-first 规则保持现有交付语义。

## 4. 准入、资源与成本

准入的执行上限最终默认为每人三个顶层工作 Run，配置可降为一。短的只读 IM 协调交互有独立的小额度，仍计入实际模型请求限流。daemon-origin 的 watcher 收尾、审批续接与恢复保留来源和优先级；不能被一个占用目录的队首饿死。队列在每个来源内保序，同时选择其他已具备资源的工作。

一次准入或入队由 control store 原子提交。运行中的集合从 Run 和队列事实推导；进程内注册表只保留取消、steer 和 watcher 句柄。崩溃恢复、领取、取消和最终释放均带 generation/claim 校验，旧进程不能对新领取结果执行效果。等待人、外部状态、资源或服务商时释放模型 worker；是否保留资源占用取决于效果是否仍在该目标上进行，未知效果先观察后重试。

冲突由可信作用域而非请求措辞判断：

- 本地写入按规范化后的物理 roots 判定；不确定能力按写入处理。只读并行须由最终实际工具集合证明，后续工具激活不能悄悄扩大能力。
- 同一 clean Git 仓库的并行写 Run 使用独立受管 worktree；第一个 direct 写 Run 准入时冻结仓库身份、初始干净状态和基准 commit。后续视图从该基准建出，当前 checkout 的中途改动不改变准入决定。dirty 起点、非 Git、子模块或无法证明基准时排队。
- Git 视图不隔离远端分支、部署、数据库和其他外部目标。可信工具/执行适配器给出规范化的目标身份、读写方式与占用期限；模型可以提出目标，但不能自行证明无冲突。未知网络、凭据或外部效果进入保守的 person 级资源通道并说明原因。资源申请必须避免持有部分资源无限等待另一部分。
- 同一视图内可写子代理默认串行；各自有已验证隔离视图时可并行。它们继承父 Run 的能力与资源预算，不能以子代理身份绕过调度和审批。
- worker 数、每人执行上限、短交互额度和 provider/model 请求配额分别计算。429 共享有界退避并支持取消；实际请求包括顶层、子代理和后台角色。活跃 Run 的模型、推理、执行根、权限模式和配置 generation 固定，设置变化只作用于以后准入的 Run 或经安全恢复的续接。

worktree 创建和登记必须幂等。交付物记录基准、分支、提交、未提交及未跟踪内容；`/apply` 先对目标当前状态完整预检，不安全或冲突时保留产物，不自动合回或部分覆盖。清理不得删除未交付工作。

## 5. 交付批次与停机线

| 批次 | 代码边界与产物 | 进入下一批的证据 |
| --- | --- | --- |
| A 归属与受众 | `gateway/httpapi` 统一事件详细/摘要投影；CLI 多窗口焦点、IM 多工作语义和失效回复边的 eval；现有每人执行上限保持一 | 两 CLI 窗口实时和回放均不串流；审批仍可跨端回答；原北极星三场景与当前 eval 通过 |
| B 持久多 Run | `control` 原子准入/队列、`gateway/httpapi` 多 Run 注册与精确停止/steer/status、启动恢复；不复制 Thread/Task 状态 | 并发领取与重启无双启、漏输入或错误目标；上限一时新路由语义有明确回归用例 |
| C 单聊多工单 | Gateway 的结构化目标优先和 Main 判断路径、IM 发出消息映射与带 ID 通知、无模型总览；CLI 各窗口保持自己的焦点与执行快照 | 单个 IM chat 操作 A/B/C；补充 A 不成为新工作；含糊输入询问；同时审批各归其 Run |
| D 隔离与调度 | `runpool` 物理 roots 和外部资源占用、受管 worktree、子代理写入保护、provider 共享配额 | 先 2、再 3 个独立工作实际并行；同目录/目标串行，未知效果保守等待且不饿死其他工作 |
| E 交付与开放 | `/apply` 与清理、跨端多任务总览、故障矩阵、安装包和 daemon 真实压测 | 所有硬门槛和北极星 eval 通过后，才把默认上限设为 3 |

每批运行 `selfmind selfcheck --fast`；发布前运行完整 `selfmind selfcheck`、文档契约、迁移升级 fixture、race 测试及 Linux/macOS 打包重启。消息路径缺陷在 `evalcases/` 录制生产路径证据；Main 的补充/转交判断至少使用两家独立 provider/协议实测，不把单一模型结果当成通用证明。

## 6. 故障矩阵与真实验收

注入点包括：准入前；队列已领取而 Run 未启动；worktree 已创建而未登记；工具效果已发生而结果未保存；提交后通知未发；取消已记录而子进程尚未退出。每一处检查输入不丢、效果不盲重试、未完成状态不被抹掉、资源不提前释放、结果与审批不发错 Run。外部效果不确定时只能观察，不能从模型文字推定未发生。

完整场景：CLI-A 处理工单 A，CLI-B 处理 B，单一 IM chat 查看两者并新建 C；在 IM 给 A 补充要求，A/C 同时要求审批，B 等待 watcher；重启 daemon 后分别续接，另一个未绑定 IM 账号无法读取任何工作。再以 A/B 同工作区、同一外部目标、不同外部目标、A 恰好结束时补充到达、IM 消息重投作反例。WeChat 和 Telegram 都保留 Phase-1 演示通道，三个北极星场景均可在一分钟内演示并有 eval。

记录每项工作的有效执行时间、队列与资源等待、429、实际并发模型请求、token/完成工作及结果交付状态。同一组独立工作相对串行基线必须有可见的执行重叠和完成时间收益，且 scorecard 的规划、工具、恢复与验证质量不退步。先在上限二观察，再在上限三做 CLI/IM/cron/watcher/子代理混合压测，最后改默认值。把上限降为一只能回退并发容量，不能伪称恢复旧版跨端输入语义。

## 7. 边界与文档同步

本计划不做 dirty/非 Git 的自动快照、多仓库组合视图、远程 Runner 或 SaaS 调度。资源身份的通用接口是本期范围；新增具体外部系统适配器以实际工作证据驱动，不能为单个工单或模型写规则。

每批落地后同步 `docs/STATUS.md`，仅在实际能力改变时更新 `AGENTS.md`，并检查 `docs/identity-continuity.md`、`docs/work-timeline.md`、`docs/worker-pool-design.md`、`docs/tool-safety.md`、`docs/command-reference.md` 和 `docs/tui-terminal-first-hybrid.md`。当前“跨端普通文字自动 steer 本人唯一活动 Run”的描述在批次 C 实现前仍是现状，届时须明确改为结构化边优先、CLI 焦点和 IM Main 判断的新契约。
